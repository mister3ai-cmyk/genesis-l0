## 1. Что это
- **Узел** — до 4 граней F0–F3 × 128 float32 (2 KB) плюс заголовок 64 B. Faces не ортонормализуются: реальные эмбеддинги, маска присутствующих граней `face_mask`.
- **Поиск в два шага:**
  1. Префильтр FACEWISE_FOLDED SRP — 256 бит на грань, расстояние min_f min(h, B − h), pool 768.
  2. Пересчёт скора на кандидатах (`rerank_core`). Гейт A1 по заголовку — **до** чтения граней.
- **Без malloc** в `hg_search_*` и `rerank_core`. Поиск — чистая функция: ничего не пишет ни в арену, ни в журнал.
- **Скорер AUTO:**
  - однородная арена → B5 = Σ_f⟨q, F_f⟩²;
  - смешанные маски → знаковый max-sim B4.
  - Однородность считается на уровне арены по счётчикам масок, узлы не сканируются.
- **Ingest по умолчанию пишет только F0.** F1/F2 приходят от источника или позже от LLM (`enrich_hook`, Message Batches). F3 не пишется.
- **Проекция `artifacts/proj_v1`** заморожена: центр + PCA 384 → 128, sha256 проверяется. Обучена на dev F0 ∪ F3, 2 × 20 000 реплик.
- **Режим Грассмана** (MGS, O(4)-инвариантный хэш, гейт A2 по октантам) — экспериментальный. O(4)-инвариантность к неортонормированным реальным граням неприменима.

## 3. Контракт шкалы доверия `trust_q16` (ingest-слой)
- **Кто назначает:** только ingest-слой по реестру источников (`source_id` → доверие), в момент записи.
  - Не LLM, не содержимое реплики и не поиск.
  - Повысить или понизить можно только через `hg_node_set_trust`, со стороны записи.
- **L2 доверие не проверяет.** Он доверяет полю как заданному. Подлинность источника — граница ответственности L0/L1 (провенанс, подписи, консенсус); см. §7.
- **Пример таблицы «источник → доверие».** Это пример контракта, а не измерение:

| Источник | trust | Комментарий |
|---|---|---|
| запись, подтверждённая провенансом L0/L1 (подпись, консенсус) | 1.00 | единственный уровень, которому L2 может доверять «полностью» |
| реплика самого пользователя в аутентифицированной сессии | 0.90 | на dev-прогоне: «user» |
| проверенная интеграция (поле CRM, календарь API) | 0.85 | — |
| ответ модели, саммари, извлечённые факты | 0.70 | на dev-прогоне: «assistant» |
| неаутентифицированный внешний текст (web, тело письма, чужой документ) | 0.50 | граница `balanced` |
| подозрительный источник | ≤ 0.30 | карантин — флагом, независимо от trust |

- **`min_trust = 0.8` (пресет `factual`) имеет смысл только относительно этой шкалы.** В примере он означает «только пользователь и подтверждённые источники, без текста модели».
- При другой шкале порог нужно пересчитать. Например, если всё пишется с нейтральным 1.0, `factual` ничего не отсекает (§9, вариант «нейтральное доверие»).

## 5. Время и замещение фактов (этапы 3–4)
- **Затухание по умолчанию выключено:** β = 0 в запросе, λ = 0 при ingest. Включается, только если источник передал `decay_lambdas` и вызывающий задал β.
  - При β = 0 или λ = 0 выдача побитово совпадает со старой (тест).
  - На dev затухание нейтрально: на половине B ни одного изменения. β* = 0.1 подобран на половине A, выигрыш — 1 вопрос из 67 [dev-H].
- **Замещение по `key_id` с учётом доверия:** узел i скрыт, если у того же ключа есть узел j новее, чистый (`anis_flags == 0`) и с `trust_j ≥ trust_i`. Результат не зависит от порядка прихода.
  - `history = True` показывает и скрытые версии.
  - Если новый узел ушёл в карантин или потерял доверие, предыдущий снова становится видимым (тест).
- **Ключи** только из явного поля источника. Правило `fact_keys` (R1–R3) — экспериментальное, заморожено на 568a8d2, по умолчанию выключено.
  - На dev оно покрыло 25 % вопросов knowledge-update; из 4 размеченных пар 2 оказались ложными; R@5 knowledge-update на половине B −11.1 [−33.3, 0] [dev-H].
- **Синтетика**, 50k узлов, 500 цепочек [синт]:
  - «текущее значение» hit@1: 0.266 без замещения → 1.000 с замещением;
  - запрос с `history`: 1.000; без флага `history` старое значение недоступно (0.000).
  - Значит, на dev механизм упирается в качество ключей, а не в сам механизм.

## 6. Модель конкурентности: один пишущий поток, много читающих (SWMR)
- **Поля, которые меняются во время поиска** (их пять): `node_flags`, `trust_q16`, `anis_flags`, `anis_score`, `decay_lambda`.
  - Запись — атомарная store с release; биты флагов — fetch_or / fetch_and.
  - Чтение в поиске — атомарная load с acquire; на x86 это обычные MOV.
- **Поля атомарны по одному, а не группой.** Поиск, идущий во время смены, может увидеть ключ на полпути: **оба узла ключа или ни одного**.
  - Запись всегда идёт в порядке «скрыть → записать поля → показать». Он не даёт поиску увидеть узел, который законченная смена скроет.
  - Ровно один видимый узел гарантирован только после возврата пишущей функции.
- **Всё остальное требует, чтобы поиск в этот момент не шёл:** вставка узлов, `hg_update_faces`, перекодирование, счётчики масок. Либо нужна новая структура арены с `n`, опубликованным после записи.
  - `srp_scratch` — одна быстрая выдача на арену в каждый момент. Адаптер сериализует запросы одного `NGPMemory` замком.
- **Проверка** [синт]: `test_concurrency.c` под `-fsanitize=thread`, gcc 15.2, 4 читающих потока + 1 пишущий.

  | Сборка | Отчёты TSan | Код выхода |
  |---|---|---|
  | атомарная | 0 | 0 (ошибок 0) |
  | негативный контроль (обычные чтения) | 12 гонок | 66 |

  Обе проверки есть и в pytest.

## 7. Модель угроз ANIS: границы
- 5 % инъекций, каждая — перефраз в пространстве эмбеддингов: cos 0.85–0.95 к атакуемому узлу.
- Поиск FACEWISE 256 бит / 768, A1 с min_trust 0.5.
- Источники: [синт] 50k узлов, 1 000 запросов на класс; [dev-F0] 135 настоящих вопросов, инъекции нацелены на реплики с ответом.

| Класс | Что это | Закрывает L2? | Числа |
|---|---|---|---|
| (a) | инъекция с низким доверием или в карантине | **да**, гейт A1 до чтения граней | Poison@10 = 0.0 % [синт] и 0.0 % [dev-F0]; по заголовку отсекается 4.3–4.8 % кандидатов; полнота без потерь |
| (b) | инъекция с нормальным доверием через доверенный канал | **нет** | Poison@10: 100 % [синт], 95.6 % [dev-F0]; на dev яд занимает 60 % мест в top-10, R@10 −1.5 п.п. |
| (c) | легитимный узел ошибочно помечен | цена ложной пометки | помеченная цель: 100 → 0 % [синт]; на dev R@10 89.6 → 88.1, на 8 затронутых вопросах 87.5 → 62.5 % |
| (d1) | более новый ложный узел того же ключа с пониженным доверием | **да** — правило замещения с учётом доверия + строгий min_trust | ниже порога A1: истина 100 % (старое правило — 0 %, отказ в обслуживании); выше порога: ложь@1 52.5 % при min_trust 0.5, **0 % при min_trust 0.8** (`factual`) [синт] |
| (d2) | более новый ложный узел того же ключа с тем же доверием канала | **нет** | ложь@1 100 % при любом правиле [синт] |

- **Граница ответственности.** От (b) и (d2) L2 не защищает и в горячем пути защищать не будет: криптографии в L2 нет.
  - Это задача ingest-слоя и L0/L1 — провенанс записи (подпись источника), консенсус, назначение `trust_q16` и `source_id` по проверенному источнику. Например, «замещать ключ может только `source_id`-владелец».
  - L2 гарантирует одно: узел с пониженным доверием или помеченный узел не попадёт в выдачу и не скроет более доверенный факт.
- **Не проверено:** инъекции-перефразы, сгенерированные настоящей LLM. Здесь только эмбеддинговые перефразы: платные вызовы в ТЗ запрещены.

## 8. Реконсолидация вне горячего пути
- **Журнал.** Обращения пишет вызывающий через `hg_access_record` в своё SPSC-кольцо (один поток пишет, один читает). Структура 192 B: head, tail и неизменяемые поля на разных cache line, в памяти вызывающего. Переполнение отбрасывает новые записи и считает их.
- **`hg_consolidate`** — пакет на стороне записи:
  - каждый узел учитывается не больше одного раза за пакет;
  - `access_count += 1`; λ_eff = max(κ·λ0, λ0 / (1 + α·c)), по умолчанию α = 0.5, κ = 0.25;
  - узлы с `anis_flags`, высоким `anis_score` или низким доверием не усиливаются;
  - результат не зависит от порядка журналов.
- **Чистота поиска** [синт]: выдача побитово одинакова на 1 / 1 / 4 / 4 потоках, заголовки не меняются.
- **Петля обратной связи** [синт, 50k узлов, β = 0.1, период полураспада 30 дней, возраст 0–365 дней]:
  - если писать в журнал весь top-10, к 8-му раунду «хабы» занимают **88 %** хвоста top-10;
  - пол κ на это почти не влияет: при κ = 0.75 — 86 %;
  - если писать только top-1, — **18 %**;
  - цель@1 и цель@10 при этом 99–100 %; 0 усиленных ANIS-узлов.
- **Решение:** горячий путь не усложняем. MCP-адаптер пишет в журнал только top-1 (по умолчанию) или то, что вызывающий отметил через `mark_used`. При β = 0 (по умолчанию) реконсолидация на ранжирование не влияет.

## 9. MCP-адаптер (`mcp_adapter.py`)
- **Интерфейс:** `query_ngp_memory(query_text, mode="balanced", min_trust=0.5, now_ts=None, top_k=10, history=False)` → список `{glyph_id, score, text, trust, created_ts, source_id, superseded, ...}`.
  - `TOOL_SCHEMA` — схема MCP-инструмента.
  - `configure(...)` создаёт общий на процесс экземпляр: модель и арена загружаются **один раз**.
  - `mark_used(ids)` и `consolidate()` — стороны журнала и записи.
- **Пресеты — наборы параметров запроса, а не веса граней** (весов граней в C нет). Пользовательский `min_trust` может только поднять порог пресета.

| Пресет | min_trust | history | β | Скорер |
|---|---|---|---|---|
| factual | ≥ 0.8 | нет | 0 | AUTO |
| balanced | ≥ 0.5 | нет | 0 | AUTO |
| episodic | ≥ 0.5 | да (видны скрытые версии) | 0 | AUTO |

- **Проверка на dev: «пресеты не вредят»** [dev-F0].
  - Путь адаптера: одна память на haystack, ingest по умолчанию (F0, `proj_v1`, без ключей). Turn recall_any.
  - Сравнение с `balanced`: парный bootstrap 10k.

| Тип вопроса | n | balanced R@5 / R@10 | factual, нейтральное доверие | episodic, нейтральное доверие | factual, контракт «user 0.9 / assistant 0.7»: R@5 / R@10 (ΔR@5 [CI]) |
|---|---|---|---|---|---|
| knowledge-update | 20 | 80.0 / 100.0 | = | = | 100.0 / 100.0 (+20.0 [+5.0, +40.0]) |
| multi-session | 36 | 80.6 / 91.7 | = | = | 91.7 / 91.7 (+11.1 [+2.8, +22.2]) |
| single-session-assistant | 17 | 88.2 / 94.1 | = | = | **5.9 / 5.9 (−82.4 [−100, −64.7])** |
| single-session-preference | 9 | 77.8 / 77.8 | = | = | 77.8 / 88.9 (0.0) |
| single-session-user | 18 | 77.8 / 83.3 | = | = | 77.8 / 83.3 (0.0) |
| temporal-reasoning | 35 | 77.1 / 80.0 | = | = | 77.1 / 82.9 (0.0) |
| все | 135 | 80.0 / 88.1 | = | = | 75.6 / 78.5 (ΔR@10 −9.6 [−15.6, −3.7]) |

- «=» значит «совпадает с `balanced` побитово». На нейтральном доверии пресеты одинаковы, потому что в dev нет ни сигнала доверия, ни ключей.
  - Это **«не вредят»**, а не «подтверждены».
  - `episodic` на dev ничего не меняет: ingest не ставит ключей, замещать нечего.
- **С примером контракта** `factual` делает ровно то, что задумано: убирает текст модели.
  - Помогает вопросам о фактах пользователя: knowledge-update +20 п.п., multi-session +11 п.п.
  - Ломает вопросы «что ты мне говорил»: single-session-assistant −82 п.п.
  - Вывод для MCP-клиента: `factual` — для фактов пользователя; вопросы о словах ассистента — через `balanced` или `episodic`.
