# hologlyph_l2 — закрытие аудита: инвариантный хэш, два recall, сравнение с HNSW

> Строк: 252 · Дата: 21.11.2026 · Ветка `feat/hologlyph-l2-grassmann` (база 467e0a3) · N = 140 000, 3 датасета, 1 000 eval + 300 tune запросов
> Содержимое: разведка формулы и данных (§1), O(4)-инвариантный хэш (§2), методика (§3), таблицы hologlyph и HNSW (§4), вывод (§5). Сырые числа — `results/*.csv`, `results/summary.json`.

## 1. Разведка (по коду, до замеров)

**Метрика поиска — `score_exact`** (`score_node` в `hologlyph.c`; отдельной функцией — `hg_score_exact`):

    Q~[16k + j] = sqrt(max(w_k, 0)) · q[16k + j]        (hg_weight_query, 8 октантов × 16)
    S(q, Y, w)  = Σ_{f=0..3} <Q~, Y_f>²  =  |Y Q~|²  =  Q~ᵀ P Q~,   P = YᵀY

- **Запрос — вектор q ∈ R¹²⁸ (ранг 1), а не подпространство.** Поэтому это не tr(P₁P₂) двух узлов.
- **Веса октантов W входят только со стороны запроса.** База от W не зависит, и ни хэш, ни граф перестраивать при смене W не нужно.

**Гейты** применяются до скора: на полном скане — для каждого узла, в быстром пути — при rerank.
- **A1 (заголовок):** `trust_q16/65535 < min_trust` (до 21.11 — `trust_scalar` f32) или `anis_score > max_anis` → узел отброшен, грани не читаются.
- **A2 (октанты):** τ_trust − τ_anis < θ, где τ — скалярные произведения 16-мерных октантов 3 и 6 **невзвешенного q с одной гранью Y₀**.
  - **Находка:** A2 зависит от выбора базиса подпространства, то есть сам не O(4)-инвариантен.
  - На 10 000 парах (узел, запрос) при Y → RY с случайной R ∈ O(4) решение A2 меняется в **20.7 %** пар; сам A2 отсеивает 13.2 % пар.
  - Логика в этом коммите не менялась. Инвариантный вариант на будущее: энергия октанта по всему подпространству, Σ_f ⟨q_oct, Y_f,oct⟩².

**Данные и «посаженный ответ»** (`bench_hologlyph.c`; генератор перенесён в `hg_benchlib.c` без изменений — тот же xorshift, тот же seed, первые 1 000 запросов совпадают со старым бенчем):
- **Узлы:** MGS от U[−1, 1]^{4×128}, 15 % «токсичных» заголовков.
- **Запрос:** узел t выбирается среди чистых; q = Σ c_f Y_f + шум (норма шума = 0.5 нормы сигнала), q нормируется; веса w_k = 0.5 + U, сумма 1.
- **Старый «recall@10» = доля запросов, где t попал в топ-10** — это recall_planted.

**Откуда 88.8 % у полного перебора** — целиком гейт A2:

| Полный перебор, N = 140k | recall_planted@10 |
|---|---|
| гейты A1 + A2, случайные веса (как в старом бенче) | **88.8 %** |
| только A1 | 100 % |
| без гейтов: случайные веса / равные 1/8 / без весов | 100 % / 100 % / 100 % |

Отсюда два recall, оба в каждой таблице:
- **recall_exact@10** — пересечение с точным топ-10 полного перебора `score_exact` **при тех же гейтах и той же маске**. У полного перебора он равен 100 % по определению; это проверено тестом.
- **recall_planted@10** — найден ли посаженный узел, по запросам, где он разрешён фильтром. Это мера данных и модели, а не индекса.

## 2. O(4)-инвариантный хэш (`HG_HASH_SUBSPACE_ENERGY`)

    e_m(Y) = Σ_f <Y_f, r_m>² = r_mᵀ P r_m,   r_m ~ N(0, I₁₂₈),  m = 0..2B−1
    узел:   бит b_m = [e_{2m}(Y) > e_{2m+1}(Y)]          — один код B бит на узел
    запрос: бит b_m = [<Q~, r_{2m}>² > <Q~, r_{2m+1}>²]   — тот же SRP по матрице r rᵀ − s sᵀ

- **Инвариантность.** (RY)ᵀ(RY) = YᵀY, поэтому код не зависит от базиса.
- **Без свёртки.** Кандидаты — top-C по обычному Хэммингу, без `min(h, B − h)`.
- **Режимы** (enum `hg_hash_mode`, старый режим сохранён):

  | Режим | Плоскости | Как задаётся бит |
  |---|---|---|
  | `FACEWISE_FOLDED` (0, старый) | B | по одной грани |
  | `SUBSPACE_ENERGY` (1) | 2B, N(0, I) | попарное сравнение энергий |
  | `SUBSPACE_ENERGY_UNIT` (2) | 2B, ‖r‖ = 1 | то же; бесследовые rrᵀ − ssᵀ |
  | `SUBSPACE_CHI2` (3) | B | порог: медиана χ²₄ = 3.3567 для узла, χ²₁ = 0.4549 для нормированного запроса |

  Режим CHI2 — только для сравнения: узел и запрос разных рангов.
- **Скан (`hg_prefilter_candidates`):**
  - дистанция обрезается до 254; 255 означает только «узел запрещён маской» и в гистограмму не попадает;
  - тай-брейк на границе пула — по номеру слота, поэтому пул не зависит от числа потоков;
  - фильтр `allow` работает во всех режимах, включая старый.
- Горячий путь без `malloc`. Плоскости генерируются один раз (xorshift + Box–Muller, seed 7), буферы выровнены на 64 B.

**Тест инвариантности** (`test_hologlyph.py::test_subspace_hash_invariance`):
- 10 000 случайных Y, R ∈ O(4) = QR гауссовой матрицы со случайной сменой знаков, включая det = −1; B = 256;
- та же `libhgbench.so`, что и в бенче.

| | float64-эталон | fp32 (боевой путь) | пограничные биты, \|e₂ₘ − e₂ₘ₊₁\| < 1e-4·масштаб |
|---|---|---|---|
| `SUBSPACE_ENERGY` | 0 узлов с отличиями | 0 флипнутых битов (вне границы 0) | 0.0096 % |
| `SUBSPACE_ENERGY_UNIT` | 0 | 0 | 0.0103 % |
| `FACEWISE_FOLDED` (старый) | — | **512 из 1 024 бит отличаются в среднем; 100 % узлов** | — |

**Остальные тесты** (7 из 7 зелёные):
- B = 256: узел с h = 256 и h = 255 попадает в пул как 254, запрещённый узел (255) — нет;
- пул на 1 и 4 потоках совпадает поэлементно;
- полный перебор = точный топ-10 numpy с маской и без;
- `hg_score_exact` = numpy;
- посаженный узел по ENERGY-Хэммингу — в медиане 1-й из 5 000.

## 3. Методика

- **Железо и софт:**
  - i5-11400H (6 ядер / 12 потоков, L3 12 MB), WSL2 Ubuntu-26, RAM 8.2 GB; частота и режим питания из WSL не управляются (governor n/a);
  - gcc 15.2.0, `-O3 -march=native -ffast-math -fopenmp`, одна сборка `libhgbench.so` для теста и бенча, `OMP_PROC_BIND=close`, без `OMP_WAIT_POLICY=active`;
  - Python 3.14.4, numpy 2.5.5, **hnswlib 0.8.0** (pip, venv `~/.venvs/hg-bench`), сборка HNSW на 6 потоках.
- **Датасеты:**
  - `random` — генератор старого бенча;
  - `clustered15`, `clustered30` — 1 000 центров; член кластера = QR(Y_c + σ·Z(I − Y_cᵀY_c)), то есть шаг в касательном пространстве и ретракция.
  - **σ задан заранее по геометрии, без запросов:** главный угол θ = arccos(‖Y_c Yᵀ‖_F / 2) — RMS-косинус четырёх главных углов; σ подобран бисекцией так, чтобы медиана θ была 15° / 30°.

  | Датасет | σ | Медиана θ | p10–p90 θ |
  |---|---|---|---|
  | clustered15 | 0.0241 | 15.01° | 14.4–15.6° |
  | clustered30 | 0.0521 | 30.02° | 29.0–31.0° |

- **Запросы:** 1 000 eval + 300 tune (разные запросы), прогрев 100.
  - На tune выбраны только B для каждого режима и ENERGY против ENERGY_UNIT. В каждом режиме победил B = 256. Энергетический вариант (`energy*`): `random` → ENERGY; `clustered15`/`30` → ENERGY_UNIT, разница с ENERGY ≤ 2.5 п.п.
  - Итоговые таблицы — только на eval.
- **Задержка:** p50 / p99 по отдельным запросам, таймер внутри C (`hg_bench_latency`), включая код запроса.
  - Python-накладные hologlyph через ctypes: p50 0.64 мс против 0.59–0.63 мс нативно (+0.01–0.05 мс).
  - HNSW мерится из Python: `knn_query` на 1 запрос + тот же C-rerank.
- **HNSW индексирует энергетические признаки:** φ(Y) = (e_m(Y) − 4)/√(2M′); для запроса φ(Q~) = (⟨Q~, r_m⟩² − ‖Q~‖²)/√(2M′); M′ = 512, `space=ip`. E⟨φ(Y), φ(Q~)⟩ = Q~ᵀPQ~ = S (из E[(rᵀAr)(rᵀBr)] = trA·trB + 2tr(AB)).
  - **flat-IP(φ)** — точный перебор по φ. Это потолок аппроксимации φ без графа.
  - Все пайплайны: top-K′ → тот же точный rerank `hg_rerank_candidates`.
  - hnswlib берёт ef = max(ef, K′), поэтому ef перебирается как {K′, 2K′, 4K′}.
- **Сценарий A** — без гейтов (у кластерных датасетов заголовки чистые).
- **Критерий смены default в мосте на ENERGY** (зафиксирован до замеров): при равной p50 recall_exact@10 на eval не ниже FACEWISE − 0.5 п.п. на всех датасетах.

**Почему инвариантный хэш слабее.**
- **Ранги разные.** Узел — ранг 4, запрос — ранг 1. Даже запрос, лежащий целиком внутри подпространства, даёт косинус между бесследовыми частями P и Q~Q~ᵀ не больше ≈ 0.49. Хэмминг такого узла — около 60° против 90° у случайного, сигнал слабый.
- **FACEWISE сравнивает запрос с отдельными гранями** (ранг 1 с рангом 1), и сигнал сильнее.
- **Неинвариантность FACEWISE на ранжирование почти не влияет.** Базис узла фиксируется один раз при вставке, а свёрнутая дистанция по лучшей грани остаётся осмысленной нижней оценкой S.

## 5. Вывод

1. **«88.8 %» — не потеря индекса, а гейт A2.** Без него полный перебор находит посаженный узел в 100 % случаев. A2 к тому же зависит от базиса: при повороте его решение меняется в 20.7 % пар.
2. **Инвариантный хэш ENERGY точно инвариантен** (0 флипов в fp32, тест) и в 4 раза компактнее (4.5 против 17.9 MB, помещается в L3, 4.3–4.8k QPS против 1.9–2.0k), **но по recall_exact проигрывает FACEWISE на 15–58 п.п.** Причина в несимметричных рангах узла и запроса. Default остаётся FACEWISE.
3. **hologlyph FACEWISE (4 потока) выигрывает у HNSW(φ) на N = 140k:**
   - точность при равной задержке: clustered15 — 98.7 % за 0.55 мс против 52–77 % у HNSW M16/M32 при p50 ≤ 0.56 мс; clustered30 — 88.1 % за 0.57 мс против 85.2 % за 0.50 мс;
   - фильтрация: 90 % и 78 % на масках 5 % и «кластерная 5 %» против 62 % и 46 % на clustered15, при этом в 12–37 раз быстрее;
   - смена весов на лету: 97.8 % против 43.2 %;
   - память индекса: коды 18 MB против графа 308–325 MB (грани 287 MB для rerank нужны обоим), построение 1.5–1.8 с против 12–388 с;
   - детерминизм: выдача 1 = 4 потока.
4. **HNSW(φ) выигрывает при одном потоке на запрос** (0.3–0.5 мс против 1.32–1.45 мс у FACEWISE) — ценой точности (52–85 % против 88–99 %). На clustered15 у HNSW выше QPS при пакете (2.9k против 1.9k), но recall 53 % против 99.8 %. Задержка HNSW почти не зависит от N.
5. **Граница применимости скана кодов:** против HNSW равной точности — около 0.26M узлов (FACEWISE, 1 поток) и около 0.6M (4 потока); скан ENERGY достигает ~1 мс около 0.3M (1 поток) и 0.6M (4 потока). Дальше линейный скан проигрывает графу. Это экстраполяция внутри одного режима памяти, а не замер HNSW на миллионах.
6. **Потолок φ при M′ = 512 высокий** (95–100 % на clustered15). Потери HNSW — в основном от графа: запросы ранга 1 лежат вне распределения базы.

## 6. Воспроизведение (WSL)

    cd hologlyph
    gcc -O3 -march=native -ffast-math -fopenmp -shared -fPIC hologlyph.c hg_benchlib.c -o libhgbench.so -lm
    python3 -m venv ~/.venvs/hg-bench && ~/.venvs/hg-bench/bin/pip install numpy hnswlib==0.8.0 pytest
    OMP_PROC_BIND=close ~/.venvs/hg-bench/bin/python -m pytest -q -s test_hologlyph.py    # 7 тестов
    OMP_PROC_BIND=close ~/.venvs/hg-bench/bin/python bench_vs_hnsw.py                     # ~25 мин, results/*.csv
    OMP_PROC_BIND=close ~/.venvs/hg-bench/bin/python bench_vs_hnsw.py --only-qps          # только таблица 4.3

Таблица 4.3 перемерена отдельно (`--only-qps`) после исправления бага. В первом прогоне временный массив запросов (`hn.ptr(Q[ev])` прямо в аргументах вызова) освобождался до того, как C его читал. Остальные таблицы этот баг не затронул.
