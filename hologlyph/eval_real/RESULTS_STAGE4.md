> Тесты: `test_writer_side.py` (10), всего 41
> Поиск: FACEWISE 256 бит / pool 768, top-10, гейт A1 (min_trust 0.5, max_anis 0.2), A2 выключен, 1 поток

## 0. Правки перед этапом
1. **Затухание по умолчанию выключено.** `decay_beta` в запросе равен 0. `decay_lambda` при ingest тоже 0, пока источник явно не передаст `decay_lambdas`. Тест проверяет оба случая: без λ и с явной λ.
2. **`fact_keys` заморожен.** Константы `EXPERIMENTAL = True` и `FROZEN_AT = "568a8d2"`. Правило работает только с флагом `key_for(..., use_rule=True)`, ingest его не вызывает. В docstring запрещено дальше подстраивать правило под dev.
3. **Замещение с учётом доверия** — `hg_supersede_key` и `hg_node_set_trust` на стороне записи, в C.
   - Узел i скрыт, если у того же `key_id` есть узел j новее по (created_ts, slot), чистый (`anis_flags == 0`) и с `trust_q16_j ≥ trust_q16_i`. Результат зависит только от набора узлов, а не от порядка их прихода.
   - Python-мост хранит индекс key → все слоты и пересчитывает ключ при каждой вставке и каждом `set_trust`.
   - Изменение trust или флагов идёт в порядке «скрыть → записать поля → показать». Поэтому карантин нового узла возвращает видимость предыдущему, а снятие карантина снова его скрывает.
   - Новый бит `HG_ANIS_QUARANTINE` (0x80000000) в `anis_flags` отсекается гейтом A1. Остальные биты справочные.
   - Тесты:
     - сценарий 1: новый узел не скрывает старый при меньшем доверии или грязных флагах;
     - сценарий 2: карантин и понижение доверия нового узла возвращают старый, обратная операция снова его скрывает;
     - пошаговая запись = пакетный `supersede_flags` на 400 узлах в случайном порядке и после 200 изменений trust/флагов;
     - бит карантина отсекается в обоих путях поиска.
4. **Модель конкурентности: один пишущий поток, много читающих** (описана в `hologlyph.h`).
   - Пять изменяемых полей — `node_flags`, `trust_q16`, `anis_flags`, `anis_score`, `decay_lambda` — пишутся атомарно с release (биты флагов через fetch_or/fetch_and). Поиск читает их через acquire; на x86 это обычные MOV.
   - Всё остальное (вставка, `hg_update_faces`, перекодирование) требует, чтобы поиски в этот момент не шли.

   **Проверка под TSan** (`test_concurrency.c`, gcc 15.2, `-fsanitize=thread`, pthreads):
   - **Нагрузка:**
     - 4 читающих потока × 600 запросов: перебор и FACEWISE, плюс журнал обращений;
     - пишущий поток одновременно: 6,55 млн переключений карантина и 409 582 консолидации, которые пишут `decay_lambda`; читатели его читают при β = 0.3.

   | Сборка | Отчёты TSan | Код выхода | Итог |
   |---|---|---|---|
   | атомарная | 0 | 0 | ошибок 0; 465 узлов усилено, кольца без потерь |
   | негативный контроль, `-DHG_PLAIN_HEADER_LOADS` | 12 гонок (score_node ↔ supersede_pass / hg_node_set_trust / st_f32) | 66 | тест действительно ловит гонку |
   | `-O3 -fopenmp`, без TSan | — | 0 | ошибок 0 |

   Это же в pytest (с 150 запросами): `test_tsan_single_writer_four_readers_and_negative_control`.

   **Ограничение:** поля атомарны по одному, а не группой. Поиск, идущий во время изменения, может увидеть ключ на полпути — оба узла или ни одного. Порядок «скрыть → записать → показать» исключает только то, что конечное состояние скроет. Ровно один видимый узел гарантирован после возврата пишущей функции.

## 4.1 Стресс-тест отравления
Инъекции — перефразы в пространстве эмбеддингов: `inj = normalize(F_t + τu)`, где u ⊥ F_t, а cos(inj, F_t) ~ U[0.85, 0.95].
- **Синтетика:** 2 500 инъекций (5 % от 50 000), по одной на атакуемый узел.
  - Запросы: 1 000 атакованных (цель атакована) и 1 000 чистых.
  - Каждый запрос — псевдозапрос `F_t + 0.35u`.
- **Dev:** 3 335 инъекций, по 5 % каждого haystack. Они нацелены на реплики с ответом своего вопроса. Поиск идёт внутри своего haystack.

Обозначения: **Poison@10** — доля запросов, у которых в top-10 есть хотя бы одна инъекция. **Цель@10** — цель в top-10 (на dev — R@10 по репликам с ответом).

|---|---|---|---|---|---|
| без атаки | атакованные цели | — | — | 100.0 | 0.0 % |
| (a) низкий trust или карантин | атакованные | **0.0** [0.0, 0.4] | 0.0 % | 100.0 | 4.3 % |

### (d) Отравление через замещение (синтетика: 50k узлов, 500 цепочек, 1 000 запросов «текущее значение»)
- В каждую цепочку добавлен один ложный узел: новее последней версии, тот же `key_id`.
- У каждой цепочки свой канал с одним доверием t_c ~ U[0.8, 1].
- Варианты атаки:
  - **d1-pass** — trust U[0.55, 0.75]: проходит A1, но ниже цепочки;
  - **d1-low** — trust U[0.1, 0.4]: ниже порога A1;
  - **d2** — trust = t_c, то есть тот же доверенный канал.
- Обозначения: **ложь@1** — ложный факт на первом месте. **Ложь@10** — он есть в top-10. **Истина@1** — первым идёт верный последний узел. **Потеряно** — в top-10 нет ни истины, ни лжи.

| Атака | Правило | min_trust | Ложь@1, % | Ложь@10, % | Истина@1, % | Потеряно, % |
|---|---|---|---|---|---|---|
| d1-pass | новый побеждает (этап 3) | 0.5 | 100.0 | 100.0 | 0.0 | 0.0 |
| d1-pass | с учётом доверия (этап 4) | 0.5 | 52.5 [49.4, 55.6] | 100.0 | 47.5 | 0.0 |
| d1-pass | новый побеждает | 0.8 | 0.0 | 0.0 | 0.0 | **100.0** |
| d1-pass | с учётом доверия | 0.8 | **0.0** | 0.0 | **100.0** | 0.0 |
| d1-low | новый побеждает | 0.5 | 0.0 | 0.0 | 0.0 | **100.0** (отказ в обслуживании) |
| d1-low | с учётом доверия | 0.5 | 0.0 | 0.0 | **100.0** | 0.0 |
| d2 | новый побеждает | 0.5 | 100.0 | 100.0 | 0.0 | 0.0 |
| d2 | с учётом доверия | 0.5 | **100.0** | 100.0 | 0.0 | 0.0 |

Выводы:
- **Правило п.3 закрывает d1.**
  - При старом правиле узел с низким доверием скрывал истину, а сам отсекался A1: факт пропадал в 100 % запросов. Теперь истина на месте в 100 %.
  - При d1-pass правило не даёт скрыть истину. Но ложный узел остаётся видимым, и запрос по теме не отличает его от верного: ложь@1 = 52.5 %. Убрать его из выдачи может только min_trust выше доверия атакующего (0.8 → ложь 0 %, истина 100 %). Это довод в пользу пресета `factual` со строгим min_trust на Этапе 5.
- **d2 правилом не закрывается и не может закрываться.** Атакующий в том же канале с тем же доверием неотличим по заголовку. Нужна защита на уровне источника, например «замещать может только тот же `source_id`, что владеет ключом», или подпись записи. Не реализовано, это решение за вами.

## 4.2 Реконсолидация вне горячего пути
- **Поиск ничего не пишет.** Обращения записывает вызывающий через `hg_access_record(log, matches, n, ts)` в свой SPSC-кольцевой буфер (один поток пишет, один читает) уже после поиска.
  - `HologlyphAccessLog`: 192 B, три отдельные cache line — head (пишущий в журнал), tail (консолидация) и неизменяемые поля. Записи — в памяти вызывающего, не рядом с заголовками.
  - Переполненное кольцо отбрасывает новые записи со счётчиком `dropped` и не затирает непрочитанное.
  - Без malloc. `HologlyphMatch` получил поле `slot`, размер остался 24 B.
- **`hg_consolidate(arena, logs, n_logs, params, seen, stats)`** — пакет на стороне записи.
  - Каждый узел учитывается не больше одного раза за пакет; дедупликация идёт по битовой карте `seen` от вызывающего, на выходе она снова нулевая.
  - `access_count += 1`, затем λ_eff = max(κ·λ0, λ0 / (1 + α·count)). λ0 сохраняется при первом обращении в бывший `reserved1`; заголовок остаётся 64 B.
  - Узлы с любыми `anis_flags`, `anis_score > max_anis` или доверием ниже min_trust **не усиливаются**.
  - Результат не зависит от порядка журналов и записей (тест).
- **Тесты (`test_writer_side.py`):**
  - поиск с журналом побитово одинаков на 1/1/4 потоках, а арена (заголовки, грани, коды) не меняется;
  - учёт раз за пакет, пропуск ANIS-узлов, пол κ достигается и не пробивается;
  - независимость от порядка журналов и отсев устаревших записей (чужой glyph_id, слот вне диапазона);
  - поведение при переполнении кольца;
  - бонус ранга ровно β·(1 − κ)·λ0·Δt и не больше.
- **Бенч на 50k:** 200 запросов при 1, 1, 4 и 4 потоках дают одинаковую выдачу, заголовки не изменились.

### Петля обратной связи (синтетика 50k)
- Условия: 8 раундов × 1 000 запросов; цели запросов равномерны, то есть интерес пользователя ни к чему не смещён.
- Затухание включено: β = 0.1, период полураспада 30 дней, возраст узлов U[0, 365] дней.
- 5 % узлов помечены ANIS (видимы, но не в карантине).
- После каждого раунда консолидируются 4 журнала.
- **Доля «хабов»** — места top-10, занятые узлами, которые усилились раньше и не являются целью запроса.

| Вариант | Цель@10, раунд 8 | Цель@1, раунд 8 | Доля хабов, раунды 2 → 8 | Мин. λ_eff/λ0 | Усилено ANIS-узлов |
|---|---|---|---|---|---|
| без консолидации | 99.8 % | 99.4 % | 0 → 0 | 1.00 | 0 |
| α 0.5, κ 0.25 (по умолчанию), в журнал весь top-10 | 99.7 % | 99.0 % | **79.7 % → 87.7 %** | 0.25 | 0 |
| α 0.5, κ 0 (без пола) | 99.7 % | 98.9 % | 79.7 % → 87.7 % | 0.20 | 0 |
| α 0.5, κ 0.75 (узкий пол) | 99.8 % | 99.3 % | 78.8 % → 85.9 % | 0.75 | 0 |
| α 5, κ 0.25 | 99.7 % | 98.9 % | 83.6 % → 87.9 % | 0.25 | 0 |
| α 0.5, κ 0.25, в журнал только top-1 | 99.8 % | 99.4 % | **2.3 % → 17.8 %** | 0.40 | 0 |

Выводы:
- **ANIS-защита работает:** 0 усиленных помеченных узлов, их λ не изменилась во всех вариантах.
- **Релевантная выдача не страдает:** цель@1 и цель@10 держатся на уровне 99–100 %.
- **Эффект «богатые богатеют» в хвосте top-10 есть, и пол κ его не сдерживает.**
  - Почему: штраф затухания β·λ0·Δt доходит до 0.84, а сходство «заполняющих» узлов около 0.01. Любое снижение λ, даже ×0.75 при узком поле, даёт бонус больше этого разброса. Поэтому всё, что хоть раз попадало в top-10, занимает хвост последующих выдач.
  - κ ограничивает бонус узла в разах от его штрафа, но не относительно сходства.
- **Сильнее всего помогает журналировать только реально использованное** (top-1 или процитированные LLM записи): хабы 18 % вместо 88 %. Это решение вызывающей стороны, C менять не нужно.
- Возможное ядерное ограничение — потолок бонуса в единицах скора: β·(λ0 − λ_eff)·Δt ≤ cap. Не реализовано, потому что требует читать `lambda0` в горячем пути. Предлагаю как вариант.
- Всё это проявляется только при включённом затухании, а по умолчанию оно выключено (β = 0).

## Итоговые ограничения этапа
- **(b) и (d2) — атакующий с нормальным доверием в доверенном канале.** Заголовок такие узлы не отличает: Poison@10 = 100 % на синтетике и 95.6 % на dev. Нужны контроль на уровне источника или подписи (`source_id` как владелец ключа, Ed25519-провенанс из ветки NGP 1.1).
- **Правило п.3 не скрывает видимую ложь d1-pass.** Скрыть её может только порог min_trust выше доверия атакующего.
- **Инъекции здесь — перефразы в пространстве эмбеддингов, а не тексты.** Перефразы, сгенерированные настоящей LLM, не проверялись: платные вызовы запрещены ТЗ.
- **recall_exact@10 на изотропной синтетике (0.66) не показатель качества индекса.** Показатель — dev-пул: 0.982.
