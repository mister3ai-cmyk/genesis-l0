# Этап 3 — замещение фактов (key_id) и временной приор (dev LongMemEval_S + синтетика)

> Строк: 97 · Дата: 21.11.2026 · Источники: dev, n = 135 (без _abs), смешанная арена 2b (50 % каждого haystack с F1/F2 от Haiku, скорер AUTO → B4), bge PCA-128; синтетика 50k · Скрипт: `stage3_dev.py` (export / run / synthetic); сырые числа: `results/stage3_dev.json`, `results/stage3_synthetic.json`

## Механика (C99, без malloc, поиск — чистая функция)
- **Флаг замещения.** `node_flags` (смещение 37, бит `HG_NODE_SUPERSEDED`) ставит **сторона записи**: при вставке узла с тем же `key_id` и более новым `created_ts` старый помечается. Если старый факт пришёл поздно, помечается сам новый пришедший.
  - Делают это `HologlyphMemory.inglyph`, индекс key → видимый слот (восстанавливается при открытии файла), и массовый `supersede_flags(key_id, created_ts)`. Тест подтверждает, что оба способа совпадают.
- **Поиск.** Флаг читается из заголовка, как A1, грани не читаются. Скрытые узлы считаются в `HologlyphStats.superseded`.
  - `HologlyphParams.search_flags & HG_SEARCH_HISTORY` показывает и скрытые («какой был адрес в 2023?»).
  - Проверено в обоих путях: полный перебор и FACEWISE → `rerank_core`.
- **Затухание** — аддитивный приор: S' = S + β·log w, где w = exp(−λ·Δt), то есть S' = S − β·λ·max(0, now_ts − created_ts).
  - `now_ts` и `decay_beta` — параметры запроса, λ — `decay_lambda` в заголовке.
  - При β = 0 или λ = 0 выдача **побитово** совпадает со старой. Тест: перебор и FACEWISE, равенство id и скоров.
- **Чистота поиска.** Два прогона на одном состоянии дают одинаковый результат на 1 и на 4 потоках, после поиска заголовки и грани не изменились (тест). Реконсолидация будет в Этапе 4.
- **Тесты:** 31 (`test_hologlyph.py` 19, `test_inglyph_v2.py` 9, `test_fact_keys.py` 3). C-бенчмарк: те же данные, planted 88.7 % (256 бит, pool 768) — без изменений.

## Как формируется key_id
Только из явного поля источника (`fact_keys.key_for(..., explicit="crm.phone")`) или по узкому правилу «объект + атрибут» (`fact_keys.fact_attribute`). Правило берёт только реплики пользователя от первого лица, и **в каждом случае нужно значение**:
- **R1 — рекорд или сумма:** «my personal best … 25:50», «I set a record of …».
- **R2 — переезд или работа:** «I moved to …», «I now work at …».
- **R3 — количество чего-то:** «I've completed 50 episodes of …», «I lead a team of 4 engineers». Нужен глагол владения или прогресса; общие слова (minutes, tips, ideas…) отбрасываются.
- `key_id = crc32(пространство | атрибут)`. Пространство — владелец фактов; на dev это haystack вопроса.
- **Важно: правило частично подогнано под dev.** Первая версия содержала R4 «my new X» (phone, apartment, car). На разборе ложных пар dev оно давало большинство ложных замещений: объект упомянут, но значения факта нет. Поэтому R4 удалено. Цифры dev ниже — после этой правки, то есть с оптимистичным смещением.

## Качество замещения на dev
Пара = (скрытый старый узел, самый свежий узел того же ключа). Разметка — по `has_answer`:
- **верно:** неверно не скрыто;
- **ложно:** старый узел — реплика с ответом, а свежий нет, то есть верный факт скрыт;
- **без разметки:** ни один узел пары не помечен; судить нельзя, такие пары не учитываются.

| Метрика | Значение |
|---|---|
| а) покрытие: knowledge-update вопросы с key_id хотя бы на одной реплике-ответе | 5 из 20 (25 %) |
| а′) из них реплика-ответ входит в цепочку (есть замещение) | 2 из 20 (10 %) |
| всего реплик с ключом / скрытых | 222 / 31 (из 74 261) |
| пар с разметкой | 4 из 31 (27 без разметки) |
| б) верных среди размеченных | 2 из 4 (50 %) |
| в) ложных среди размеченных (верный факт скрыт) | 2 из 4 (50 %) |

4 размеченные пары — слишком мало для оценки точности. Вывод только качественный: правило по тексту слишком часто ошибается, чтобы включать его по умолчанию.

**Выводы:**
- **Затухание на dev нейтрально.** На B ни одного изменения. Выигрыш β = 0.1 на A — один вопрос. Включать по умолчанию не за что, но и не вредит.
- **Замещение с ключами по правилу** ни один тип не роняет за пределы CI: у knowledge-update верхняя граница CI = 0. Но направление отрицательное: −1 вопрос из 9 на B, −1 из 20 на всех.
- **Механизм потери.** Скрытие старой реплики с ответом не поднимает новую: свежий узел того же ключа может стоять ниже пятого места (пример — «personal best»). Кроме того, часть вопросов knowledge-update спрашивает старое и новое значение сразу («сколько инженеров было в начале и сколько сейчас?»). Для таких нужен `history`.
- **Решение по умолчанию:** замещение включается только для ключей из **явного поля источника**. Правило `fact_attribute` — опция, по умолчанию выключено. Ingest ставит `key_id` только если его передали.

## Синтетика (50k узлов, 500 цепочек по 3–6 версий, 2 000 запросов)
Типы запросов:
- 40 % — «текущее значение»: запрос = тема цепочки + шум, значение он знать не может; верный ответ — самая свежая версия;
- 30 % — «старое значение»: запрос = эта версия + шум, `history = True`;
- 30 % — обычные узлы без ключа.

Запросы одни и те же для всех вариантов.

| Поиск | Замещение | Запрос | n | hit@1 | hit@5 |
|---|---|---|---|---|---|
| точный | выкл | текущее значение | 792 | 0.266 | 0.956 |
| точный | вкл | текущее значение | 792 | **1.000** | 1.000 |
| точный | вкл, `history = True` | старое значение | 597 | 1.000 | 1.000 |
| точный | вкл, флаг history забыт | старое значение | 597 | 0.000 | 0.000 |
| точный | вкл | обычный узел | 611 | 1.000 | 1.000 |
| FACEWISE 256 / 768 | выкл | текущее значение | 792 | 0.266 | 0.956 |
| FACEWISE 256 / 768 | вкл | текущее значение | 792 | **1.000** | 1.000 |
| FACEWISE 256 / 768 | вкл, `history = True` | старое значение | 597 | 1.000 | 1.000 |
| FACEWISE 256 / 768 | вкл | обычный узел | 611 | 1.000 | 1.000 |

- При верных ключах замещение решает задачу «текущего значения» полностью: hit@1 0.27 → 1.00.
- `history` возвращает старые значения.
- Узлы без ключа не деградируют.
- 30 % исторических запросов показывают обратную сторону: без флага `history` старое значение недоступно (0.000). Это ожидаемо, и вызывающая сторона должна сама решать, нужен ли флаг.
- На синтетике цепочки и ключи заданы точно. Значит, ограничение на dev — в **качестве ключей**, а не в механизме.

## Известные ограничения
- **Смещение B4 к обогащённым узлам** (Этап 2b, смешанная арена dev): 67.6 % обогащённых в top-10 при 50.8 % среди релевантных реплик (58.6 % среди релевантных попаданий в top-10). Пока не калибруется. В однородной арене смещения нет.
- Замещение скрывает старое, но не поднимает новое: свежий узел ключа должен сам пройти ранжирование.
- Цифры dev по ключам частично подогнаны: R4 убрано после разбора dev. Решающая проверка — test-сплит или ключи от реального источника.
